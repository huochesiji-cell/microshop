## 一、Pod 探针（liveness / readiness / startup）

### 1.1 三种探针的核心区别

| 探针 | 回答的问题 | 失败后果 |
|------|-----------|---------|
| **startupProbe** | 启动完成了吗？ | 不启用 liveness/readiness，等它通过 |
| **readinessProbe** | 能接请求吗？ | 标记 NotReady，从 Service 摘除，**不重启** |
| **livenessProbe** | 还活着吗？ | **杀掉容器重启** |

**简单来说**：Readiness 摘流（不重启）、Liveness 杀容器（重启）、Startup 护启动。

### 1.2 Liveness 实验：容器"假死"触发重启

```yaml
# 模拟运行 30 秒后删除健康文件的容器
apiVersion: v1
kind: Pod
metadata:
  name: liveness-demo
  namespace: k8s-practice
spec:
  containers:
  - name: liveness
    image: busybox:1.28
    command:
    - /bin/sh
    - -c
    - |
      touch /tmp/healthy
      sleep 30 && rm -f /tmp/healthy &   # 30 秒后删除健康文件
      while true; do echo "running"; sleep 10; done
    livenessProbe:
      exec:                              # 执行命令判断健康
        command: [cat, /tmp/healthy]
      initialDelaySeconds: 5             # 启动 5 秒后才检查
      periodSeconds: 5                   # 每 5 秒一次
      failureThreshold: 3                # 连续 3 次失败才重启
```

**观察结果**：`RESTARTS` 列从 0 → 1 → 2 → 3，每约 45 秒重启一次。

### 1.3 Readiness 实验：容器活着但未就绪

Nginx 默认没有 `/healthz` 路径，readiness 探针 HTTP GET 返回 404，导致 READY 一直 0/1。

```yaml
readinessProbe:
  httpGet:                       # HTTP GET 检查
    path: /healthz               # 检查路径不存在 → 404 → NotReady
    port: 80
  periodSeconds: 3
  failureThreshold: 2
```

**观察结果**：`kubectl get pod` 显示 `Running` 但 `READY 0/1`。修复（创建 `/healthz` 文件）后变 1/1。

### 1.4 三个关键知识点

1. **重启陷阱**：容器重启后是全新文件系统，之前修复的文件会丢失，导致无限重启（CrashLoopBackOff）。
2. **RESTARTS 是计数器**：只增不减，像汽车里程表，永不回 0。
3. **重启退避策略**：连续重启会指数级延长等待时间（10s → 20s → 40s → ... 最大 5min）。

### 1.5 解决方案：startupProbe + postStart

```yaml
startupProbe:                     # 慢启动保护
  httpGet:
    path: /                       # 检查根路径（总能通过）
    port: 80
  failureThreshold: 30            # 最多等 150 秒
lifecycle:
  postStart:                      # 启动后自动创建文件
    exec:
      command: [sh, -c, "echo OK > /usr/share/nginx/html/healthz"]
```

## 二、Deployment 滚动更新

### 2.1 Pod vs Deployment

| | Pod | Deployment |
|------|-----|-----------|
| 管理方式 | 手动 | 自动 |
| Pod 挂了 | 没人管 | 自动重建 |
| 版本更新 | 手动删除重建 | 滚动更新 |
| 回滚 | 无 | 一键回滚 |

### 2.2 滚动更新参数

```yaml
spec:
  replicas: 3
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 1            # 更新时最多比期望副本多 1 个
      maxUnavailable: 0      # 更新时不允许有不可用 Pod
```

**参数含义**：
- `maxSurge`：更新过程中，允许临时**超出**期望副本数的 Pod 数量（加快更新速度）
- `maxUnavailable`：更新过程中，允许**不可用**的 Pod 数量（0 表示始终满血运行）

### 2.3 滚动更新流程

```
Step 1: 3 个旧 Pod（nginx:alpine）
Step 2: 新建 1 个新 Pod（maxSurge=1，最多多 1 个）
Step 3: 新 Pod Running → 杀 1 个旧 Pod（maxUnavailable=0，保证 3 个可用）
Step 4: 循环直到全部替换
```

### 2.4 更新命令与回滚

```bash
# 更新镜像版本
kubectl set image deploy/web-app nginx=nginx:1.19-alpine

# 查看发布状态
kubectl rollout status deploy/web-app

# 查看发布历史
kubectl rollout history deploy/web-app

# 一键回滚到上一个版本
kubectl rollout undo deploy/web-app
```

**为什么回滚快？** Deployment 默认保留 10 个历史 ReplicaSet，每个 ReplicaSet 对应一个版本，`rollout undo` 只是切换目标 ReplicaSet，不是重新构建。

## 三、Service 四种类型

### 3.1 Service 是什么

Pod IP 是临时的（重建后变化），Service 提供固定 ClusterIP（虚拟 IP）+ 标签选择器 + 负载均衡。

```
用户 → Service (ClusterIP 固定) → kube-proxy DNAT → 后端 Pod（IP 可变）
```

### 3.2 四种类型对比

| 类型 | 访问方式 | 使用场景 |
|------|---------|---------|
| **ClusterIP** | 仅集群内部 | Pod 之间互相调用（默认类型） |
| **NodePort** | 任意节点 IP:30000-32767 | 开发调试、简单外部访问 |
| **LoadBalancer** | 云厂商 LB 分配公网 IP | 生产环境外部入口 |
| **ExternalName** | CNAME 映射到外部域名 | 访问集群外部服务 |

### 3.3 本次实验（ClusterIP + NodePort）

```yaml
# ClusterIP
spec:
  type: ClusterIP
  selector: {app: svc-backend}
  ports: [{port: 80, targetPort: 80}]   # port=Service端口, targetPort=Pod端口

# NodePort
spec:
  type: NodePort
  selector: {app: svc-backend}
  ports: [{port: 80, targetPort: 80, nodePort: 30080}]
```

**验证方式**：
- ClusterIP：集群内 `kubectl run` 一个 busybox Pod，`wget http://svc-clusterip`
- NodePort：浏览器直接访问 `http://<任意节点IP>:30080`，三台节点都能通

## 四、调度策略

### 4.1 调度器工作流程

```
Pod 创建请求
  │
  ▼
① 过滤（Filter）：哪些节点能跑？排除内存不足/端口冲突/污点不匹配/标签不匹配
  │
  ▼
② 打分（Score）：剩余节点谁最合适？剩余资源多、镜像已缓存、Pod 分散
  │
  ▼
③ 绑定（Bind）：选最优节点，kubelet 在该节点启动容器
```

### 4.2 智能调度（默认行为）

不设任何调度限制时，调度器自动最优分配。实验：4 副本 Deployment 自动平均分布到 node1/node2 各 2 个，master 因为污点被排除。

### 4.3 nodeSelector（最简单的手动调度）

```yaml
spec:
  nodeSelector:
    node-role: compute   # 只调度到有这个标签的节点
```

```bash
kubectl label node k8s-node1 node-role=compute   # 打标签
kubectl label node k8s-node1 node-role-          # 移除标签（key 后加 -）
```

### 4.4 Taint + Toleration（污点与容忍）

- **Taint（污点）**：节点属性，表示"禁止普通 Pod 调度到这里"
- **Toleration（容忍）**：Pod 属性，表示"我有权限调度到有污点的节点"

```bash
# 给节点加污点（key=value:effect）
kubectl taint node k8s-node1 dedicated=compute:NoSchedule

# 移除污点（effect 后加 -）
kubectl taint node k8s-node1 dedicated=compute:NoSchedule-

# 查看节点污点
kubectl describe node k8s-master | grep Taints
# 输出：node-role.kubernetes.io/master:NoSchedule
```

```yaml
# Pod 声明容忍
spec:
  tolerations:
  - key: "dedicated"
    operator: "Equal"
    value: "compute"
    effect: "NoSchedule"
```

**污点三种 effect**：
- `NoSchedule`：新 Pod 不调度（已运行的不管）
- `PreferNoSchedule`：尽量不调度（软限制）
- `NoExecute`：新 Pod 不调度 + 驱逐已运行的 Pod

## 五、Requests vs Limits + QoS

### 5.1 两个概念

| 概念 | 含义 | 作用 |
|------|------|------|
| **Requests** | 我要多少资源 | 调度器预留资源，决定调度到哪 |
| **Limits** | 我最多用多少资源 | 运行时封顶，超了 CPU 被限流/内存被 OOM |

**类比**：Requests = 餐厅订座（保证有座），Limits = 最多坐几个人（可以少坐）。

### 5.2 三个 QoS 等级

| QoS 等级 | 判定规则 | 优先级 |
|---------|---------|--------|
| **Guaranteed** | 每个容器 requests == limits | 🥇 最高，最不易被杀 |
| **Burstable** | requests < limits（或不完整） | 🥈 中等 |
| **BestEffort** | 完全没设 requests/limits | 🥉 最低，最先被杀 |

### 5.3 内存不足时的驱逐顺序

```
节点内存告急 → kubelet 驱逐顺序：
  1. BestEffort（没承诺资源，杀了无影响）
  2. Burstable 中超出 requests 的 Pod
  3. Guaranteed（除非 OOM 且无其他可驱逐对象）
```

### 5.4 实验验证

```yaml
# Guaranteed
resources:
  requests: {cpu: "500m", memory: "256Mi"}
  limits:   {cpu: "500m", memory: "256Mi"}

# Burstable
resources:
  requests: {cpu: "250m", memory: "128Mi"}
  limits:   {cpu: "1", memory: "512Mi"}

# BestEffort：什么都不设
```

```bash
kubectl describe pod qos-guaranteed | grep "QoS Class"   # Guaranteed
kubectl describe pod qos-burstable   | grep "QoS Class"   # Burstable
kubectl describe pod qos-besteffort  | grep "QoS Class"   # BestEffort
```

## 原理图解

### Pod 生命周期全景

```
                    ┌─────────────────────────────┐
                    │        Pod 生命周期          │
                    └─────────────────────────────┘
  Pending ──→ Running ──→ Succeeded（正常退出）
                 │  │
                 │  └──→ Failed（异常退出）
                 │
                 ├─ startupProbe 通过后
                 │   ├─ readinessProbe 持续检查 → 决定能否接流量
                 │   └─ livenessProbe 持续检查 → 决定是否重启
                 │
                 └─ 容器重启 = 全新文件系统（RESTARTS 计数 +1）
```

### Deployment 滚动更新数据流

```
kubectl set image deploy/web-app nginx=nginx:1.19-alpine
    │
    ▼
Deployment Controller 发现期望镜像 ≠ 实际镜像
    │
    ▼
创建新 ReplicaSet（保留旧 ReplicaSet 用于回滚）
    │
    ▼
按 maxSurge/maxUnavailable 逐批替换 Pod
    │
    ▼
全部替换完成 → 旧 ReplicaSet 缩到 0（但记录保留）
```

### Service 流量转发

```
外部请求 ──→ NodePort:30080（每台节点都监听）
                  │
                  ▼
             kube-proxy（iptables DNAT）
                  │
                  ▼
             Service ClusterIP
                  │
                  ▼
        轮流转发给后端 Pod（Endpoints）
```

### 调度决策流程

```
Pod 创建请求
    │
    ▼
过滤阶段（硬性条件，不满足就排除）
    ├─ 资源够吗？（Requests 匹配）
    ├─ 标签匹配吗？（nodeSelector）
    ├─ 污点容忍吗？（Toleration）
    └─ 端口冲突吗？
    │
    ▼
打分阶段（软性条件，择优）
    ├─ 剩余资源多 → 高分（分散负载）
    ├─ 镜像已缓存 → 高分（启动快）
    └─ Pod 分散 → 高分（高可用）
    │
    ▼
绑定节点 → kubelet 启动容器
```

## 常见问题排查

### 问题 1：Pod 一直 ContainerCreating

**现象**：`kubectl get pod` 显示 Pod 状态 ContainerCreating 很久

**排查**：
```bash
kubectl describe pod <pod名> | tail -10
# 看 Events 里的 Reason，常见：
# Pulling image → 拉镜像卡住（网络/代理问题）
# FailedMount → 挂载卷失败
```

**本项目遇到的实际问题**：k8s-node1 上没有 nginx:alpine 镜像缓存，从 Docker Hub 拉取超时（`unauthorized`）。解决：在 k8s-node2 上把镜像推到本地 Harbor，k8s-node1 从 Harbor 内网拉取。

### 问题 2：Pod 无限重启 CrashLoopBackOff

**现象**：`kubectl get pod` 显示 `CrashLoopBackOff`，RESTARTS 不断增长

**原因**：容器启动后立刻崩溃（liveness 探针失败、应用启动报错、依赖未就绪）

**排查**：
```bash
kubectl logs <pod名> --previous   # 查看上一次容器崩溃的日志
kubectl describe pod <pod名> | grep -A10 "Last State"
```

### 问题 3：Service 访问不通

**现象**：curl Service ClusterIP 超时

**排查**：
```bash
# 1. Service 的 selector 是否匹配 Pod 的 label？
kubectl get svc -o wide          # 看 SELECTOR
kubectl get pod --show-labels    # 看 Pod 标签

# 2. Endpoints 是否为空？
kubectl get endpoints <svc名>    # 空的话说明 selector 没匹配到 Pod

# 3. Pod 是否 Ready？
kubectl get pod -o wide          # 看 READY 列
```

**最经典的坑**：Service 的 `selector.app` 拼错，和 Pod 的 label 对不上，导致 Endpoints 为空。

### 问题 4：终端报 `-bash: !': event not found`

**现象**：命令里带 `!` 符号时 bash 报错

**原因**：bash 把 `!` 当作历史命令扩展符号

**解决**：避免在命令行里用 `!`，或改用 `set +H` 关闭历史扩展，或用单引号包裹（`'...'` 里 `!` 不会被解释）。

## 生产环境建议

1. **探针必配**：生产环境每个服务都应配 readiness（保证流量只进就绪实例）和 liveness（自动恢复僵死进程），慢启动应用加 startupProbe。
2. **滚动更新策略**：`maxUnavailable=0` 保证更新期间服务不中断；`maxSurge` 根据剩余资源合理设置。
3. **Requests/Limits 必设**：所有生产 Pod 都应设 requests（保证调度公平）和 limits（防止单个 Pod 吃光节点资源影响邻居）。禁止裸跑 BestEffort。
4. **污点规划**：给专用节点（GPU、SSD、数据库）打污点，避免普通 Pod 抢占。
5. **Service 选型**：外部入口统一走 Ingress + LoadBalancer，不要暴露大量 NodePort（难管理、有安全风险）。
