## 一、kube-proxy 工作原理

### 1.1 Service 的 ClusterIP 是虚拟的

Service 的 ClusterIP 不对应任何真实网卡，纯粹是虚拟地址。真实转发靠 **kube-proxy** 在每台节点上生成的底层规则。

### 1.2 iptables 模式 vs IPVS 模式

| 维度 | iptables（默认） | IPVS |
|------|-----------------|------|
| 数据结构 | 线性规则链 | 内核哈希表 |
| 查找复杂度 | O(n) 逐条匹配 | O(1) 哈希查找 |
| 负载均衡 | 概率随机 | 真算法（轮询/最少连接/加权） |
| Service 数量影响 | 越多越慢 | 不受影响 |
| 更新方式 | 全量重刷 | 增量更新 |

**查看当前模式**：
```bash
kubectl get cm kube-proxy -n kube-system -o yaml | grep -i mode
# mode: "" 空值 = 默认 iptables 模式
```

> 💡 1000 个 Service 时，iptables 一个包可能要匹配上千条规则；IPVS 用哈希表 O(1) 直达后端。生产大规模集群必用 IPVS。

## 二、iptables DNAT 规则链追踪

### 2.1 完整转发路径

```
请求 http://Service:80
    │
    ▼
① PREROUTING → KUBE-SERVICES 链
    │  匹配目标 = ClusterIP:port
    ▼
② KUBE-SVC-xxx 链（Service 链）
    │  概率负载均衡，选一个后端 Pod
    ▼
③ KUBE-SEP-xxx 链（Pod 链）
    │  DNAT: ClusterIP:port → Pod IP:port
    ▼
④ 转发到真实 Pod
```

### 2.2 追踪命令

```bash
# 找到 Service 的规则
iptables -t nat -L -n | grep "<ClusterIP>"

# 看 Service 链（负载均衡）
iptables -t nat -L KUBE-SVC-<hash> -n

# 看 Pod 链（DNAT 最终动作）
iptables -t nat -L KUBE-SEP-<hash> -n
```

### 2.3 概率负载均衡原理

```bash
KUBE-SEP-xxx1  statistic mode random probability 0.33333333349  (≈1/3)
KUBE-SEP-xxx2  statistic mode random probability 0.50000000000  (≈1/2)
KUBE-SEP-xxx3  （无 probability，兜底）
```

**为什么用递减概率而不是均匀 1/3？**

iptables 规则从上到下顺序匹配（first-match wins）。如果三条都写 1/3：
- 第一条命中 1/3
- 第二条命中 (1-1/3)×1/3 = 22.2%
- 第三条命中 (1-1/3-2/9)×1/3 = 14.8%

分配不均！所以用递增概率（1/3, 1/2, 1）补偿顺序匹配的偏差，实现近似均匀。

## 三、Nginx Ingress Controller

### 3.1 Ingress 解决什么问题

```
没有 Ingress（用 NodePort）：
  前端 → 30080，订单 → 30081，用户 → 30082
  → 每个服务一个端口，难管理

有了 Ingress：
  所有服务走一个入口 :80/:443
  → 按域名/路径路由到不同 Service
```

### 3.2 Ingress 部署要点

1. 镜像来自 `registry.k8s.io`，国内直连失败，需走 Docker 代理拉取或推 Harbor
2. 涉及两个镜像：`controller`（主程序）+ `kube-webhook-certgen`（生成证书的 Job）

### 3.3 踩坑：时钟偏移导致证书失效

```
报错：x509: certificate has expired or is not yet valid:
      current time is before <证书生效时间>
```

**根因**：certgen Job 生成证书的节点时钟快了约 20 分钟，导致证书"生效时间在未来"。

**解决**：
1. 同步所有节点时钟（`ntpdate` 或手动 `date -s`）
2. 删除失效的 webhook 校验：`kubectl delete validatingwebhookconfiguration ingress-nginx-admission`

> 💡 **生产环境必须同步时钟**：K8s 各节点时钟不同步会导致证书校验失败、etcd 选举异常、日志时间错乱。

### 3.4 踩坑：rewrite-target 注解

裸写 `rewrite-target: /` 会导致 nginx 配置渲染异常（Ingress 规则丢失）。正确用法用正则捕获组：

```yaml
annotations:
  nginx.ingress.kubernetes.io/rewrite-target: /$1   # 引用捕获组
spec:
  rules:
  - host: fruit.local
    http:
      paths:
      - path: /apple(/|$)(.*)      # (.*) 被 $1 引用
        pathType: Prefix
        backend:
          service: {name: apple-svc, port: {number: 5678}}
```

### 3.5 Host 头匹配问题

Ingress 的 `host: fruit.local` 要求请求的 Host 头精确匹配。浏览器用 IP 访问时 Host 头是 IP，不匹配 → 404。

**解决**：Windows hosts 文件添加 `192.168.182.168  fruit.local`，浏览器访问 `http://fruit.local:32170/apple`。

## 四、NFS Server + StorageClass + PV/PVC

### 4.1 核心概念关系

```
┌──────┐  请求  ┌─────────┐  绑定  ┌────┐  指向  ┌──────────┐
│ PVC  │ ─────→ │ Storage │ ─────→ │ PV │ ─────→ │ NFS 存储 │
│申请1G │       │ Class   │        │物理卷│        │ 实际数据 │
└──────┘        └─────────┘        └────┘        └──────────┘
```

- **PV**：管理员准备的存储（一块"磁盘"）
- **PVC**：用户申请存储（"我要 1G"）
- **StorageClass**：动态供应自动化（PVC 一申请自动建 PV）

### 4.2 NFS Server 搭建（devops）

```bash
yum install -y nfs-utils rpcbind
mkdir -p /data/nfs
cat > /etc/exports << 'EOF'
/data/nfs 192.168.182.0/24(rw,sync,no_root_squash,no_subtree_check)
EOF
systemctl start rpcbind nfs
exportfs -rv
```

**exports 参数**：
| 参数 | 含义 |
|------|------|
| rw | 读写 |
| sync | 同步写入（可靠，稍慢） |
| no_root_squash | 客户端 root 保留权限（K8s 挂载需要） |
| no_subtree_check | 不检查子目录（避免权限问题） |

### 4.3 K8s 节点装 NFS 客户端

```bash
yum install -y nfs-utils
showmount -e 192.168.182.167   # 验证连通性
```

### 4.4 NFS Provisioner + StorageClass

核心组件：`nfs-subdir-external-provisioner`，功能是 PVC 申请时自动在 NFS 上创建子目录 + 建 PV + 绑定。

关键配置（环境变量）：
```yaml
env:
  - name: NFS_SERVER
    value: "192.168.182.167"    # NFS 服务器
  - name: NFS_PATH
    value: "/data/nfs"          # 共享路径
```

### 4.5 验证动态供应全链路

```bash
# 1. 创建 PVC
kubectl apply -f test-pvc.yaml   # 申请 1Gi

# 2. 查看 PVC 自动 Bound + PV 自动创建
kubectl get pvc                   # Status: Bound
kubectl get pv                    # 自动创建 pvc-xxx

# 3. devops 上自动生成子目录
ls /data/nfs/                     # 出现 k8s-practice-test-pvc-pvc-xxx/

# 4. 挂载到 Pod 写数据
# Pod 内 echo 'Hello' > /data/test.txt

# 5. 验证数据持久化（删 Pod 数据还在）
kubectl delete pod xxx
cat /data/nfs/k8s-practice-test-pvc-pvc-*/test.txt   # 数据还在！
```

## 原理图解

### Service 流量转发全景

```
外部请求
    │
    ├─ NodePort 模式 → 节点 IP:30000-32767 → kube-proxy DNAT
    ├─ ClusterIP 模式 → 集群内 ClusterIP → kube-proxy DNAT
    └─ Ingress 模式 → Nginx Controller → 按域名/路径路由
         │
         ▼
    kube-proxy（iptables/IPVS 规则）
         │
         ▼
    后端 Pod（Endpoints）
```

### 动态供应流程

```
用户创建 PVC（storageClassName: nfs-client）
    │
    ▼
StorageClass 找到对应 provisioner
    │
    ▼
provisioner 在 NFS 上创建子目录
    │
    ▼
自动创建 PV 并绑定 PVC
    │
    ▼
PVC Status = Bound，可被 Pod 挂载
```

## 常见问题排查

### 问题 1：Ingress 返回 404

**现象**：curl 或浏览器访问 Ingress 返回 404

**排查**：
```bash
# 1. 看 Ingress 后端是否关联正确
kubectl describe ingress <name> -n <ns>

# 2. 看 controller 日志
kubectl logs -n ingress-nginx <controller-pod> --tail 30

# 3. 看 nginx 配置里有没有加载规则
kubectl exec -n ingress-nginx <controller-pod> -- cat /etc/nginx/nginx.conf | grep <host>
```

**常见原因**：
- Host 头不匹配（浏览器用 IP 访问，规则里写的是域名）
- rewrite-target 注解写法错误（导致规则渲染失败）
- 后端 Service 的 selector 和 Pod 标签不匹配

### 问题 2：Pod 卡在 Terminating

**现象**：`kubectl delete pod` 后 Pod 一直 Terminating

**原因**：节点上的容器或挂载卷删不掉（NFS 挂载卡死、容器进程不退出）

**解决**：
```bash
kubectl delete pod <name> --force --grace-period=0
```

### 问题 3：PVC 一直 Pending

**现象**：`kubectl get pvc` 状态 Pending

**排查**：
```bash
kubectl describe pvc <name>   # 看 Events 里的原因
```

**常见原因**：
- StorageClass 不存在或 provisioner 没运行
- provisioner 连不上 NFS Server（IP 错误、防火墙、网络不通）
- NFS Server 未导出目录（`exportfs -rv` 没执行）

## 生产环境建议

1. **网络**：大规模集群切 IPVS 模式；Service 用 ClusterIP 内部通信，外部统一走 Ingress + LoadBalancer
2. **时钟**：所有节点配 chrony 同步内网 NTP，禁止直连公网 NTP
3. **存储**：动态供应是标配；NFS 适合共享读场景，数据库等高性能场景用本地盘/云盘 + StatefulSet
4. **NFS 高可用**：学习环境单点 NFS，生产应配 NFS 高可用（DRBD/Keepalived）或改用 Ceph/云盘
5. **镜像**：生产环境所有镜像走内部 Harbor，节点禁止直连公网镜像仓库
6. **静态 IP**：所有服务器必须配静态 IP，DHCP 会导致 IP 漂移破坏集群
