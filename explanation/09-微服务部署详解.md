## 二、操作步骤

### Step 1：编写 3 个微服务代码 + Dockerfile

**设计原则**：学习环境用**轻量方案**（Python Flask + 静态页）替代真实的 React/Java 编译，聚焦「K8s 部署」而非「业务代码语法」。简历写 React/Java 时，实际生产会用对应技术栈，部署流程完全一致。

前端 `index.html` 用原生 `fetch('/api/orders')`、`fetch('/api/users')` 调后端，验证微服务互通。

订单服务 `app.py` 核心：**从环境变量读配置**（12-Factor 配置外部化）。

```python
def get_conn():
    return pymysql.connect(
        host=os.environ.get('DB_HOST', 'mysql'),      # 不写死 IP，读环境变量
        password=os.environ.get('DB_PASSWORD', ''),   # 密码从 Secret 注入
        ...
    )
```

**为什么用 `os.environ.get()`？** 代码里不写死 IP/密码，运行时从环境变量读，K8s 用 ConfigMap/Secret 把环境变量注入 Pod。这样同一份镜像，改配置**不用重新构建**，只改 ConfigMap 重启即可。

### Step 2：构建镜像 + 推 Harbor

```bash
docker build -t 192.168.182.166/library/orders:1.0 /root/microshop/orders/
docker push  192.168.182.166/library/orders:1.0
```

Dockerfile 里用**清华 PyPI 镜像**加速（国内直连 pypi.org 慢）：

```dockerfile
RUN pip install -i https://pypi.tuna.tsinghua.edu.cn/simple --no-cache-dir -r requirements.txt
```

中间件镜像（MySQL/Redis）也从 Docker Hub 拉取后**中转推 Harbor**，这样 K8s 节点内网拉取，不依赖 Docker Hub。

> 💡 **Harbor 镜像层去重**：推送 users 镜像时输出 `Mounted from library/orders`——因为 orders 和 users 共用 `python:3.9-alpine` 基础层，仓库里已有这层就直接复用，不再上传。Harbor 是内容寻址存储（content-addressed），相同层全局去重。

### Step 3：编写 K8s YAML（9 个文件）

```
00-namespace.yaml   命名空间
01-secret.yaml      MySQL 密码（敏感）
02-configmap.yaml   DB/Redis 地址（非敏感）+ MySQL 初始化 SQL
03-mysql.yaml       PVC + Deployment + Service
04-redis.yaml       Deployment + Service
05-orders.yaml      Deployment + Service
06-users.yaml       Deployment + Service
07-frontend.yaml    Deployment + Service
08-ingress.yaml     七层路由
```

### Step 4：部署底座层（MySQL + Redis）

MySQL 关键配置：

```yaml
env:
- name: MYSQL_ROOT_PASSWORD
  valueFrom:
    secretKeyRef: {name: mysql-secret, key: MYSQL_ROOT_PASSWORD}  # 密码走 Secret
args:
  - --innodb_flush_method=fsync      # NFS 不支持 O_DIRECT
  - --innodb_use_native_aio=0        # NFS 不支持原生 AIO
volumeMounts:
- {name: data, mountPath: /var/lib/mysql}              # 数据持久化到 NFS
- {name: init, mountPath: /docker-entrypoint-initdb.d} # 首次启动自动建库建表
```

### Step 5：部署应用层 + Ingress

Ingress 七层路由（无 host 限制，任意 Host 都能匹配）：

```yaml
paths:
- {path: /api/orders, pathType: Prefix, backend: {service: {name: orders, port: {number: 5000}}}}
- {path: /api/users,  pathType: Prefix, backend: {service: {name: users,  port: {number: 5000}}}}
- {path: /,           pathType: Prefix, backend: {service: {name: frontend, port: {number: 80}}}}
```

### Step 6：验证全链路 + 持久化

```bash
curl http://192.168.182.168:32170/api/orders   # 返回 3 条订单（MySQL 通）
curl http://192.168.182.168:32170/api/users    # 返回 visit_count（Redis 通）

# 删 Pod 验证持久化
kubectl delete pod -n microshop -l app=mysql   # 模拟 Pod 漂移
# 新 Pod 起来后订单数据还在 → NFS PVC 持久化生效
```

## 三、核心知识点

### 3.1 ConfigMap vs Secret

| 维度 | ConfigMap | Secret |
|------|-----------|--------|
| 用途 | 非敏感配置（地址、库名、端口） | 敏感数据（密码、Token、证书） |
| 存储 | 明文 | base64 编码（**不是加密！**） |
| 大小限制 | 1MB | 1MB |
| 典型场景 | DB_HOST、REDIS_PORT | 数据库密码、API Key |

**Secret 真的安全吗？** base64 只是编码不是加密，`echo xxx | base64 -d` 就能解开。Secret 的安全性依赖：RBAC 权限控制（谁能 `kubectl get secret`）+ etcd 静态加密。生产环境建议用 `stringData` 之外的更安全方案（如 Kubernetes Secrets Store CSI、Vault）。

### 3.2 服务发现：为什么写服务名不写 IP？

YAML 里 `DB_HOST: "mysql"`，而不是 MySQL Pod 的 IP。因为 Pod IP 是临时的（重建后变化），而 Service 名通过 **CoreDNS** 稳定解析：

```
orders Pod 访问 mysql:3306
    → 补全为 mysql.microshop.svc.cluster.local
    → CoreDNS 解析 → mysql Service 的 ClusterIP
    → kube-proxy DNAT → 后端 MySQL Pod（IP 可变）
```

MySQL Pod 重启换 IP 了，服务名不变，订单服务不用改任何配置——**微服务解耦的核心**。

### 3.3 有状态应用用 PVC

MySQL 的数据不能丢，所以挂 PVC（NFS 动态供应）。删 Pod 重建后，新 Pod 重新挂载同一个 PVC，数据还在。

> **Deployment vs StatefulSet**：单副本 MySQL 用 Deployment 够用；多副本数据库（如 MySQL 主从、Redis Sentinel）需要 **StatefulSet**——保证 Pod 有稳定身份（`mysql-0`、`mysql-1`）+ 每个 Pod 独立的 PVC。Day 4 部署 Redis Sentinel 时再深入。

## 四、踩坑：Calico 跨节点隧道失效（重点排查案例）

### 现象

前端能访问（返回静态页），但订单/用户接口报错：

```
订单：{"code":1,"error":"Can't connect to MySQL server on 'mysql' ([Errno -3] Try again)"}
用户：{"code":1,"error":"Error -3 connecting to redis:6379. Try again."}
```

`Errno -3` = `EAI_AGAIN`，DNS 临时解析失败。

### 排查过程（按顺序）

1. **Service/Endpoints 正常**：`kubectl get endpoints` 非空，selector 匹配没问题
2. **DNS 解析失败**：`gethostbyname('mysql')` 报 `Errno -3`
3. **绕过 DNS 直接测 TCP**：`create_connection(('10.96.161.166',3306))` 也超时 → **不是 DNS 问题，是网络问题**
4. **看 Pod 分布**：orders 在 node1（10.244.36.x），mysql 在 node2（10.244.169.x），CoreDNS 在 master——全是跨节点
5. **看 calico-node 状态**：

```
calico-node-dsgb5   0/1   Running   192.168.182.165   k8s-node1   ← NotReady + 旧 IP！
```

### 根因

宿主机重启 → DHCP 重新分配 → node1 IP 从 `.165` 变成 `.168`。但：

1. **kubelet 正确上报了新 IP**（`kubectl get nodes` 显示 `.168`）
2. **Calico 的 calico-node Pod 还死咬着旧 IP `.165`**——因为 hostNetwork Pod 的 podIP 在**创建时就固定**，容器重启也不会更新
3. Calico 用这个 podIP 建立 IPIP 隧道，隧道还指向已不存在的 `.165`
4. 结果：node1 所有**跨节点**流量断裂

**为什么之前没发现？** node1 上跑的业务（Ingress + 前端 + 订单 + 用户 + Redis）都是「同节点通信」，跨节点的只有 MySQL（node2）和 CoreDNS（master）。直到微服务真正跨节点调用才暴露。

### 修复

```bash
# 删掉 IP 还是旧值的 calico-node pod，让 DaemonSet 用新 IP 重建
kubectl delete pod -n kube-system calico-node-dsgb5
```

新 pod 探测到 `.168`，重新建立 IPIP 隧道，跨节点通信恢复。

### 教训

1. **服务器必须静态 IP**，DHCP 会导致 IP 漂移破坏 CNI 隧道
2. **改 IP 后必须重启 CNI**（Calico/Flannel）让它重新探测节点 IP
3. 排查「Service 访问不通」时，先 `get endpoints`（看 selector），再测 TCP（区分 DNS 还是网络），最后看 Pod 分布（判断是否跨节点）

## 七、常见问题排查

### 问题 1：Pod 内 DNS 解析失败（Errno -3）

**现象**：应用报 `[Errno -3] Try again` 或 `Temporary failure in name resolution`

**排查**：
```bash
# 1. CoreDNS 是否运行
kubectl get pods -n kube-system | grep coredns

# 2. 绕过 DNS 直接测 TCP（区分 DNS 还是网络）
kubectl exec <pod> -- python -c "import socket; socket.create_connection(('10.96.x.x',3306),3)"

# 3. 看 Pod 分布（是否跨节点）
kubectl get pods -o wide
```

**本项目根因**：Calico 跨节点隧道因节点 IP 变更失效（见第四节），不是 CoreDNS 本身的问题。

### 问题 2：MySQL 跑在 NFS 上启动失败

**现象**：MySQL Pod 启动报 O_DIRECT 或 AIO 错误，反复重启

**原因**：MySQL 默认用 `O_DIRECT`（绕过 OS 缓存直接写盘）+ 原生 AIO，NFS 两者都不支持

**解决**：加参数 `--innodb_flush_method=fsync` + `--innodb_use_native_aio=0`

> ⚠️ **生产环境数据库绝不用 NFS**（性能差 + 数据一致性风险），用本地盘/云盘 + StatefulSet。本项目用 NFS 是学习环境特例。

### 问题 3：mysql 客户端命令行带密码卡住

**现象**：`mysql -uroot -p'密码'` 执行后卡住不动

**原因**：密码含特殊字符 + 引号解析问题，mysql 没读到密码，退到交互式等待输入（kubectl exec 无 TTY 就挂起）

**解决**：从容器环境变量读密码，避免手动输入：
```bash
kubectl exec <pod> -- sh -c 'mysql -uroot -p"$MYSQL_ROOT_PASSWORD" -e "..."'
```

## 八、生产环境建议

1. **配置管理**：Secret 用 Vault/Secrets Store CSI，禁止把密码明文提交代码仓库；用 GitOps（ArgoCD）管理 YAML
2. **数据库**：MySQL 用 StatefulSet + 本地盘/云盘，不用 NFS；配置主从高可用
3. **副本数**：无状态服务 replicas ≥ 2 + 反亲和，保证单节点故障不影响服务
4. **探针**：readiness 探针应该真正检查依赖（如 DB 连通性），不能只返回 "ok"
5. **资源限制**：所有 Pod 设 requests/limits，禁止裸跑 BestEffort
6. **静态 IP + CNI 重探测**：服务器配静态 IP，改 IP 后重启 Calico/Flannel
7. **镜像安全**：Harbor 集成 Trivy 扫描，禁止使用 `latest` 标签，用语义化版本
