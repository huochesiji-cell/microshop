## 一、Prometheus 生态组件职责

| 组件 | 作用 | 端口 |
|------|------|------|
| **Prometheus** | 核心：定时抓取指标、存储、告警规则评估 | 9090 |
| **node-exporter** | 采集节点 CPU/内存/磁盘/网络（每节点一个 DaemonSet） | 9100 |
| **kube-state-metrics** | 采集 K8s 对象状态（Pod/Deployment 数量等） | 8080 |
| **Prometheus Operator** | 用 CRD（ServiceMonitor/PrometheusRule）管理监控配置 | 443 |
| **Grafana** | 可视化（图表 + Dashboard） | 80 |
| **Alertmanager** | 告警去重/分组/路由/通知 | 9093 |
| **config-reloader** | 边车：监听配置变化并热加载 Prometheus/Alertmanager | - |

```
数据流：
  node-exporter / kube-state-metrics / kubelet(cAdvisor)
        │ 暴露 /metrics
        ▼
  Prometheus（按 ServiceMonitor 抓取 → 存储 TSDB → 评估规则）
        │ firing 告警
        ▼
  Alertmanager（去重/分组/路由）
        │ webhook/邮件/企业微信
        ▼
  通知接收方
```

## 二、部署步骤

### Step 1：Helm 安装 + 镜像中转

```bash
# Windows 浏览器下载 helm 二进制 → MobaXterm 拖到 master
tar -zxvf helm-v3.12.3-linux-amd64.tar.gz && mv linux-amd64/helm /usr/local/bin/helm

# 添加仓库 + 拉取兼容 K8s 1.23 的版本
helm repo add prometheus-community https://prometheus-community.github.io/helm-charts
helm pull prometheus-community/kube-prometheus-stack --version 48.6.0
```

**镜像中转**（中国网络核心步骤）：把 9 个监控镜像从 quay.io/docker.io/registry.k8s.io 拉到本地 → 打 Harbor 标签 → 推送：

```bash
for img in quay.io/prometheus/prometheus:v2.45.0 ... ; do
  docker pull $img
  name=$(echo $img | sed 's#.*/##; s#:.*##'); tag=$(echo $img | sed 's#.*:##')
  docker tag $img 192.168.182.166/library/$name:$tag
  docker push 192.168.182.166/library/$name:$tag
done
```

### Step 2：values.yaml 定制（镜像 + 资源限制）

**关键坑**：prometheus/alertmanager/node-exporter 等组件有默认 `registry` 字段（quay.io），只改 `repository` 会得到 `quay.io/192.168.182.166/...` 错误地址。正确写法：

```yaml
prometheus:
  prometheusSpec:
    image:
      registry: 192.168.182.166/library   # registry 指向 Harbor
      repository: prometheus               # repository 只留镜像名
      tag: v2.45.0
    resources:
      requests: {memory: "512Mi", cpu: "200m"}
      limits:   {memory: "1Gi", cpu: "1"}
```

### Step 3：helm install

```bash
helm install kube-prometheus-stack kube-prometheus-stack/ \
  -f /root/kube-prometheus-values.yaml --namespace monitoring --create-namespace
```

## 三、4 大类指标 + PromQL

| 前缀 | 来源 | 含义 |
|------|------|------|
| `node_*` | node-exporter | 节点资源（CPU/内存/磁盘/网络） |
| `container_*` | kubelet cAdvisor | 容器级资源 |
| `kube_*` | kube-state-metrics | K8s 对象状态 |
| `apiserver_*` | API Server | 请求延迟/错误率 |

**核心 PromQL**：

```promql
# 过滤 + 聚合
sum(kube_pod_status_phase{phase="Running"})

# 按维度分组
sum by (namespace) (kube_pod_status_phase{phase="Running"})

# 排序取前 N
topk(3, node_memory_MemAvailable_bytes)

# counter 必须 rate 算速率
rate(node_cpu_seconds_total{mode="idle"}[5m])
```

counter 类型（只增不减）直接画图是一条向上的线，必须 `rate()[5m]` 算「窗口内每秒增量」才有意义。`irate` 是瞬时速率（对抖动敏感），`rate` 更平滑。

## 五、Alertmanager 告警 + Webhook

### 5.1 告警链路

```
Prometheus 评估 PrometheusRule → firing → Alertmanager → 去重/分组/路由 → Webhook
```

### 5.2 自定义 PrometheusRule

```yaml
apiVersion: monitoring.coreos.com/v1
kind: PrometheusRule
metadata:
  name: custom-alerts
  namespace: monitoring
  labels:
    release: kube-prometheus-stack   # 关键：必须带这个标签才会被 Prometheus 加载
spec:
  groups:
  - name: microshop-alerts
    rules:
    - alert: NodeMemoryOver50
      expr: (1 - node_memory_MemAvailable_bytes / node_memory_MemTotal_bytes) > 0.5
      for: 1m
      labels: {severity: warning}
      annotations:
        description: "节点 {{ $labels.instance }} 内存使用率 {{ $value | humanizePercentage }}"
```

### 5.3 Alertmanager 配置（关键机制）

**两个层次**：
- `alertmanager.config` → 配置**内容**，生成 Secret
- `alertmanager.alertmanagerSpec.configSecret` → CR **引用**哪个 Secret

两者都要配，否则 operator 用默认 null 配置：

```yaml
alertmanager:
  config:
    route:
      receiver: webhook
      group_by: ['alertname']
    receivers:
    - name: webhook
      webhook_configs:
      - url: 'http://192.168.182.164:5000/webhook'
    - name: "null"        # 默认子路由(Watchdog→null)需要这个接收器
  alertmanagerSpec:
    configSecret: alertmanager-kube-prometheus-stack-alertmanager
```

## 六、原理图解

### 监控数据流全景

```
┌─────────────┐   ┌──────────────────┐   ┌──────────────┐
│ node-exporter│   │kube-state-metrics │   │ kubelet       │
│ (节点指标)   │   │ (K8s 对象指标)    │   │ cAdvisor(容器)│
└──────┬──────┘   └────────┬─────────┘   └──────┬───────┘
       │  /metrics          │  /metrics           │
       └────────────────────┼────────────────────┘
                            ▼
                 ┌─────────────────────┐
                 │      Prometheus      │  ← ServiceMonitor 决定抓谁
                 │  抓取→TSDB→规则评估   │
                 └──────────┬──────────┘
                            │ firing 告警
                            ▼
                 ┌─────────────────────┐
                 │    Alertmanager      │  ← 去重/分组/路由
                 └──────────┬──────────┘
                            │ webhook/邮件/企业微信
                            ▼
                       通知接收方
```

### 告警三状态

```
inactive（条件不满足）→ pending（满足但未满 for 时长）→ firing（触发通知）
```

## 八、常见问题排查

### 问题 1：Grafana 图表 No Data（数据源测试正常）

**现象**：Save & test 成功，但所有图表 No Data

**排查**：查客户端时钟 vs 服务器时钟。本案例：VM 挂起导致虚拟机时钟慢 15.5 小时，浏览器（Windows）时钟正常，Grafana 按「未来」时间窗口查询 → No Data。

**解决**：`date -s` 对齐所有节点时钟；治本用 chrony/open-vm-tools 同步。

### 问题 2：镜像拉取失败（EOF / unauthorized / TLS handshake timeout）

**现象**：批量拉镜像时部分失败

**原因**：
- `EOF` / `TLS handshake timeout`：代理瞬时抖动，重试即可
- `unauthorized`：Docker Hub 对代理节点 IP 匿名限流

**解决**：重试；或改用国内镜像源（如 `docker.m.daocloud.io/grafana/grafana:10.1.0`）。

### 问题 3：Helm values 镜像地址变成 `quay.io/192.168.182.166/...`

**现象**：渲染出 `quay.io/192.168.182.166/library/prometheus`

**原因**：这些组件有默认 `registry` 字段，只改 `repository` 会被拼上默认 registry 前缀

**解决**：`registry` 设成 Harbor 地址，`repository` 只留镜像名。

### 问题 4：自定义 PrometheusRule 不生效

**现象**：`kubectl apply` 成功，但 `/api/v1/alerts` 查不到

**原因**：Prometheus 的 `ruleSelector` 要求 `release: kube-prometheus-stack` 标签，自定义规则没带

**解决**：`kubectl label prometheusrule <name> -n monitoring release=kube-prometheus-stack`

### 问题 5：operator 报 `undefined receiver "null" used in route`

**现象**：Alertmanager 配置初始化失败，告警一直走 null

**原因**：Helm 深合并导致「路由引用 null 接收器，但 receivers 里没有 null」。`receivers` 列表被整体替换，但默认的 `route.routes`（Watchdog→null）被合并保留。

**解决**：在 `receivers` 里补一个 `- name: "null"` 接收器。

### 问题 6：Python 日志重定向后「消失」

**现象**：`python script.py > log` 后日志文件长时间空

**原因**：Python 的 print 重定向到文件时是**块缓冲**，内容不立即写盘

**解决**：`python -u script.py > log`（无缓冲）或加 `sys.stdout.flush()`。

## 九、生产环境建议

1. **时钟同步**：所有节点配 chrony 同步内网 NTP，禁止手动 date -s 长期维持
2. **镜像**：所有监控镜像走内部 Harbor，节点禁直连 quay.io/docker.io；配置国内加速器
3. **告警分级**：按 severity 路由（critical 走电话/短信，warning 走邮件），设置抑制规则避免告警风暴
4. **通知渠道**：企业微信群机器人需要格式适配器（prometheus-webhook-dingtalk/weixin）
5. **资源限制**：Prometheus 按数据量调 retention（`--storage.tsdb.retention.time`），ES 类组件限制堆内存
6. **高可用**：Prometheus 可配 Thanos/Cortex 做远程存储 + 多副本，Alertmanager 集群模式去重
7. **持久化**：Prometheus TSDB 挂 PVC（本学习项目没挂，重启丢历史数据）
